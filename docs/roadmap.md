## ✅ M5 — Browse backups as a folder (completed, 2026-11-16)

The GVfs `delta://` backend was replaced by "Browse as a folder": a read-only mount with `borg mount`, on demand, in the
native variant only.

- **Done and verified in a real session (NixOS, GNOME, Nautilus):** a button in the versions window
  (`MountSnapshot`/`UnmountSnapshot`); opening interrupts the running backup, which resumes when the folder is closed; a
  scheduled backup is postponed with a single notification; `Status` = `browsing`; it closes when the session is locked or
  suspended (with a logind inhibitor), when the window is closed, when the client disappears and after 2–3 minutes without use
  (`/proc`: open files, working directory, watched folders; a long copy keeps its source open and is not cut off); `CanMount`
  hides the button in a Flatpak.
- Original criterion (discarded): browse `delta:///` in Nautilus without patches.
- **Findings (verified with `scripts/verify_borg_mount.sh`, Borg 1.4.5 on NixOS):** `borg mount` works (it brings `pyfuse3`;
  `fusermount3` has the right permissions and `/dev/fuse` is accessible) and `borg list` works with the mount active, but with the
  repository **mounted, `borg create` fails** (`Failed to create/acquire the lock`): a permanent mount would block the automatic
  backups. Also, a GVfs backend is a C plugin against GVfs's internal libraries, with no stable API outside its tree, which
  conflicts with "a single language, Python" and with Flatpak.
- The versions window (M4) already covers browsing backups and extracting only what is chosen (`ListFolder`, `PreviewVersion`)
  without mounting anything.
- If it is taken up again: "Browse backups as a folder", a read-only mount managed by the daemon **on demand** with
  `borg mount`, with no `delta://` scheme of its own and no index. What it adds: thumbnails, "Open with…", dragging to restore
  and random access to large files (video, RAW).
- **Decision (2026-11-14, the user): browsing wins over copying.** Opening a backup interrupts the running backup (Borg cannot
  be paused: `SIGINT` and a resume from the last checkpoint, with the interruption mechanism from M2) and postpones the
  scheduled ones. The daemon watches the window that asked for the mount: when it closes (or goes away) it unmounts and starts
  the backup again. So that a forgotten window does not leave the computer without backups, the daemon closes and unmounts it
  when the computer **suspends** and when the session is **locked**. This replaces "always unmount before a backup".
- **Decision (2026-11-16, the user): two variants.** The mount only exists in the **native** version; the **Flatpak** mounts
  nothing and is managed only from Delta's UI (versions, preview, folder browser, restore: M4). Reason: a FUSE mount inside the
  sandbox is not visible to Nautilus (it runs on the host) and needs broad device permissions. It is implemented with a
  `SnapshotMounter` port: the `borg mount` adapter is only registered in the native variant; the daemon exposes `CanMount` and
  the UI hides "Browse as a folder" when it is false.
- **Verified (2026-11-16, `scripts/verify_mount_vs_backup.sh`, Borg 1.4.4):**
  - `borg mount` is refused while a `borg create` runs; with a backup mounted, the backup does not start.
  - A single `SIGINT` does not release the repository in the middle of a large file; the second (`INSIST_AFTER`, 5 s) does
    (exit code 130). The window can take about 5 s to open: the UI must show "preparing the backup".
  - With a file open, `borg umount` fails (`Device or resource busy`). `SIGTERM` to the mount process releases the repository
    but **leaves the folder mounted**: after killing it, always run `fusermount3 -u -z`.
  - `.checkpoint` files remain; the `prune` of the next successful backup removes them.

## 🚧 M7 — Polish and the 1.0 release

The i18n base (gettext and `po/`) has been in since M1; here: complete the translations, accessibility, documentation,
packaging (a native package; Flatpak as a secondary target) and the final license (proposed: GPL-3.0-or-later).

Decisions (2026-11-16, the user):

- **Native minimum base: GNOME 46+ (libadwaita 1.5, GTK 4.10, Python ≥ 3.12).** Fedora, Arch, openSUSE Tumbleweed and
  Leap 16, Gentoo, NixOS, AlmaLinux and Rocky 10. AlmaLinux/Rocky 9 and Leap 15.6 (GNOME < 46) are served with Flatpak, which
  brings its own runtime. The exact versions of each distribution are checked in CI with containers, not from memory.
- **Two distribution variants, and the documentation explains why:**
  - **Native (window and FUSE):** the GTK4 app, the Nautilus extension and "Browse as a folder" (`borg mount`).
  - **Flatpak (window only):** the GTK4 app with versions, preview, browser and restore. No mount: a FUSE mount in the sandbox
    is not seen by Nautilus (it runs on the host) and would need broad device permissions. To be designed: scheduling backups
    without `systemd --user` (the Background portal or a timer of its own).
- **Version compatibility:** of Borg (1.2, 1.4, 2.0 in the Flatpak and in existing repositories), of Nautilus and
  nautilus-python, and prebuilt packages (rpm, AUR, a Flatpak bundle).
- **Documentation with Astro (Starlight) and bun**, in `website/`: static, light and dark themes, responsive, accessible, in
  American English and European Spanish, published on GitHub Pages (the `web` and `deploy` jobs of `.github/workflows/ci.yml`,
  after the tests and the mutation tests). The screenshots are generated by a script (`scripts/make_screenshots.py`) that
  renders the windows with sample data, never showing real files.

Tasks, in order:

1. ✅ Translations (2026-11-16): `po/delta.pot` regenerated, `es.po` complete (also Delta's technical messages; the text from
   Borg and the system is left as it is) and a test that checks that no text is left untranslated.
2. 🚧 Accessibility: the audit and the fixes are done (`ui/a11y.py`: names for icon-only controls, check boxes and spinners,
   decorative icons hidden, alternative text for the preview, no dimmed text on data). Still to try with Orca and keyboard only
   in a real session.

   (`scripts/ci/check_mutants.sh`), and builds, checks and publishes the website from `main`; CodeQL runs in its own workflow. The
   first real run showed that the environment sync failed from scratch (the project's build backend, `poetry-core`, was not in a new
   virtualenv), which `scripts/sync-venv.sh` now avoids. The distributions are checked apart (`distros.yml`, by hand and weekly; it
   does not block a pull request): Fedora, Arch, openSUSE Tumbleweed, AlmaLinux 10, Rocky 10, Ubuntu 24.04 and Debian 13, each
   with the packages it ships and its own Python, with no uv and nothing from PyPI (`scripts/ci/install-deps.sh`), a check of the

4. 🚧 Flatpak: a manifest, window only, scheduling without systemd. Decision (2026-11-17, the user): **a background daemon**
   that schedules with a timer of its own. Done: `domain/recurrence.py` (when a schedule fires: hourly/daily/weekly/monthly… and
   `[days] *-*-* HH:MM`, without systemd), `infrastructure/timer_scheduler.py` (the same `Scheduler` port: it looks at the clock
   every minute and recovers **once** a backup missed while the computer was off, like `Persistent=true`),
   `infrastructure/runtime.py` (`in_flatpak()`) and the wiring: in a sandbox nothing is mounted, there is no logind session and
   the scheduler is the internal one. Also done: the Background portal (`background_portal.py`, which asks for the permission

   installed on the computer (Files loads its extensions from the system, not from a Flatpak). A Flatpak and a native install
   cannot live together in the same session (they share the D-Bus name). For Flathub the Python modules must come from pinned
   sources without network access (`flatpak/README.md`); the background permission still has to be tried with the Flatpak
   portals active. The previews of a Flatpak are unpacked in the application's cache folder, because the service and the window
